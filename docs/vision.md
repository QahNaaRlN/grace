# Grace --- архитектурное видение и направление развития

## 1. Назначение документа

Этот документ фиксирует целевое видение Grace и служит ориентиром для
будущего развития и переработки текущей реализации.

Grace должен развиваться не как очередной трекер расходов, а как
персональная система финансового здоровья: приложение хранит финансовую
модель пользователя, помогает понимать происходящее с деньгами,
прогнозировать обязательства и использовать ИИ как интеллектуальный
интерфейс поверх достоверных структурированных данных.

Ключевой принцип:

> **Grace содержит финансовую систему, а ИИ умеет ею пользоваться.**

ИИ не должен быть источником истины, хранилищем финансового состояния
или обязательным условием работы приложения.

------------------------------------------------------------------------

## 2. Продуктовое видение

Grace должен отвечать не только на вопрос «сколько я потратил?», но и на
более содержательные вопросы:

-   куда фактически ушла последняя зарплата или аванс;
-   сколько денег уходит на питание в среднем;
-   из чего состоит продуктовая корзина;
-   какие расходы выросли относительно предыдущих периодов;
-   какие обязательные платежи предстоят;
-   сколько денег останется после обязательных платежей;
-   какие платежи относятся к кредитам, рассрочкам и другим
    обязательствам;
-   какие операции являются переводами между собственными счетами и не
    должны считаться расходами;
-   какие регулярные расходы и подписки существуют;
-   как меняется денежный поток пользователя;
-   почему финансовое положение изменилось;
-   какие финансовые события требуют внимания.

Таким образом, Grace должен хранить не только банковские операции, но и
их **финансовый смысл**.

------------------------------------------------------------------------

## 3. Основные архитектурные принципы

### 3.1. Финансовое ядро независимо от ИИ

Все детерминированные операции выполняются кодом Grace:

-   хранение операций;
-   расчёт остатков;
-   агрегация расходов;
-   расчёт статистики;
-   учёт обязательств;
-   графики платежей;
-   расчёт денежных потоков;
-   правила категоризации;
-   поиск регулярных платежей;
-   построение финансовых периодов.

ИИ занимается прежде всего:

-   интерпретацией;
-   распознаванием неструктурированных данных;
-   объяснением;
-   предложением классификации;
-   выбором необходимых инструментов Grace;
-   диалоговым взаимодействием с пользователем.

Модель не должна самостоятельно выполнять финансовую арифметику, если
эти вычисления можно детерминированно выполнить на стороне Grace.

### 3.2. База данных является источником истины

Финансовое состояние пользователя хранится в собственной базе данных
Grace.

Нельзя строить архитектуру вокруг:

-   памяти языковой модели;
-   истории чата;
-   таблицы, которой управляет ИИ;
-   локального состояния React;
-   текста предыдущих ответов ассистента.

ИИ получает только необходимый контекст из Grace.

### 3.3. Клиенты не содержат критическую бизнес-логику

React-клиент является представлением системы, а не финансовым ядром.

В будущем Grace может иметь несколько клиентов:

-   Web --- React;
-   iOS --- Swift/SwiftUI;
-   потенциально Android;
-   другие интерфейсы.

Все они должны работать с одной предметной моделью через Grace API.

### 3.4. API является стабильной границей системы

Целевая схема:

``` text
React Web ─────┐
               │
SwiftUI iOS ───┼──→ Grace API (Go) ──→ Financial Domain
               │                           │
Other Client ──┘                           ├── PostgreSQL
                                           ├── Object Storage
                                           └── AI Layer
```

## 4. Репозиторий

Существующие `grace-core` и `grace-flow` целесообразно объединить в один
репозиторий.

Это один продукт с общим жизненным циклом. Большинство продуктовых
изменений будут одновременно затрагивать базу данных, Go API и клиент.

Разделение на разные репозитории создаёт ненужную координацию версий и
изменений API.

При этом объединение репозиториев **не означает смешивание приложений**.

Рекомендуемая первоначальная структура:

``` text
grace/
├── web/
│   ├── src/
│   ├── package.json
│   └── vite.config.ts
│
├── cmd/
│   └── api/
│       └── main.go
│
├── internal/
│   ├── accounts/
│   ├── transactions/
│   ├── categories/
│   ├── receipts/
│   ├── obligations/
│   ├── analytics/
│   └── assistant/
│
├── api/
│   └── openapi.yaml
│
├── migrations/
├── docs/
├── deployments/
├── compose.yaml
├── Makefile
├── go.mod
└── README.md
```

При появлении нескольких полноценных клиентов структура может
эволюционировать:

``` text
grace/
├── clients/
│   ├── web/
│   └── ios/
├── cmd/
├── internal/
├── api/
├── migrations/
└── ...
```

Нет необходимости вводить `clients/` или `apps/` заранее.

## 5. Предметная модель

Первоначальный набор сущностей должен формироваться из реальных
финансовых сценариев, а не из абстрактной схемы «обычного приложения
расходов».

Базовые сущности:

``` text
User

Account
├── debit
├── credit
├── installment
└── cash

Transaction
├── amount
├── direction
├── account
├── merchant
├── category
├── timestamp
└── source

Category

Merchant

Receipt
└── ReceiptItem

Income

Obligation
├── balance
├── payment_schedule
├── grace_period
└── minimum_payment

CategorizationRule
```

Позднее из них формируются вычисляемые представления:

``` text
MonthlySpending
FoodBasket
RecurringExpense
CashFlow
CashFlowForecast
DebtLoad
FinancialSummary
```

## 6. Операция и финансовое событие

Обычной банковской строки недостаточно для качественной аналитики.

Например:

``` text
-25 000 RUB
```

сама по себе почти ничего не сообщает.

Это может быть:

-   покупка;
-   аренда;
-   перевод между собственными счетами;
-   погашение кредитной карты;
-   погашение задолженности;
-   инвестиция;
-   снятие наличных.

Поэтому необходимо различать **техническую операцию** и её **финансовую
семантику**.

Пример:

``` text
IncomeReceived
DebtPayment
RentPayment
InstallmentPayment
InternalTransfer
Purchase
Refund
```

Это позволит отвечать на вопросы уровня:

> Что произошло с последним авансом?

вместо простого вывода списка банковских строк.

Не обязательно сразу реализовывать полноценную событийную архитектуру
(event sourcing). Речь идёт прежде всего о явном представлении семантики
финансовых событий в предметной модели.

------------------------------------------------------------------------

## 7. Модель Go backend

Не рекомендуется строить весь backend как набор глобальных
горизонтальных каталогов:

``` text
controllers/
services/
repositories/
models/
```

Предпочтительнее группировка по предметным областям:

``` text
internal/
├── accounts/
├── transactions/
├── categories/
├── receipts/
├── obligations/
├── analytics/
└── assistant/
```

Каждый модуль может содержать собственные:

``` text
domain.go
service.go
repository.go
http.go
```

если такая детализация действительно требуется.

Основной принцип --- код, относящийся к одной предметной области, должен
находиться рядом.

На ранней стадии следует избегать чрезмерной абстракции и микросервисной
архитектуры. Один модульный Go backend достаточен.

------------------------------------------------------------------------

## 8. API и несколько клиентов

Контракт между backend и клиентами должен быть формализован.

Рекомендуемый подход:

``` text
Go API
  ↓
OpenAPI
  ├──→ generated TypeScript client
  └──→ generated Swift client
```

Это позволит избежать ручного дублирования DTO и расхождений между Go,
TypeScript и будущим Swift.

React и SwiftUI не обязаны разделять UI-код.

Например:

``` text
React:
<TransactionCard />

SwiftUI:
TransactionCard
```

Это нормальное дублирование представления.

Разделяться должна не реализация интерфейса, а единая семантика:

``` text
Transaction
Account
Receipt
Obligation
FinancialSummary
```

------------------------------------------------------------------------

## 9. ИИ как отдельный слой

Первоначально ИИ не требует отдельного сервиса.

Достаточно модуля внутри Go backend:

``` text
internal/
└── assistant/
    ├── orchestrator.go
    ├── tools.go
    ├── context.go
    ├── provider.go
    └── prompts/
```

Направление зависимостей:

``` text
                assistant
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
 transactions   analytics   obligations
        │           │           │
        └──── financial core ────┘
```

Финансовые модули не должны зависеть от `assistant`.

Это позволяет:

-   полностью отключить ИИ;
-   заменить поставщика модели;
-   использовать несколько моделей;
-   тестировать финансовую систему без LLM;
-   не связывать корректность расчётов с поведением модели.

------------------------------------------------------------------------

## 10. Интеграция ИИ

Для пользовательского приложения следует использовать API языковых
моделей, а не CLI как runtime-механизм.

CLI-инструменты полезны для разработки Grace, но плохо подходят для
обслуживания пользовательских запросов.

Схема:

``` text
React / iOS
     ↓
Grace API
     ↓
AI Orchestrator
     ↓
LLM Provider API
```

Ключи поставщиков ИИ никогда не передаются клиенту.

------------------------------------------------------------------------

## 11. Инструменты ИИ

Вместо передачи модели всей финансовой истории Grace предоставляет ей
ограниченный набор инструментов.

Например:

``` text
get_accounts()
get_transactions(period, category)
get_spending_summary(period)
get_food_statistics(period)
get_recurring_payments()
get_obligations()
get_upcoming_obligations()
get_cashflow_forecast()
```

Пользователь может спросить:

> Сколько я потратил на питание после аванса?

Модель определяет необходимые действия, вызывает инструмент Grace,
получает детерминированный результат и объясняет его пользователю.

### Читающие и изменяющие инструменты

Инструменты необходимо разделять.

Читающие:

``` text
get_transactions
get_balance
get_statistics
get_obligations
```

Изменяющие:

``` text
create_transaction
change_category
delete_transaction
create_obligation
```

Изменения финансовых данных, инициированные ИИ, должны иметь более
строгие правила.

В критичных случаях используется подтверждение пользователя:

``` text
ИИ:
«Похоже, перевод 5 500 ₽ является платежом по рассрочке.»

[Подтвердить] [Изменить] [Игнорировать]
```

------------------------------------------------------------------------

## 12. Распознавание чеков

Чеки являются важным источником более детальной финансовой информации.

Процесс:

``` text
photo
  ↓
object storage
  ↓
vision / extraction
  ↓
ReceiptDraft
  ↓
user confirmation
  ↓
Receipt + ReceiptItems
```

ИИ может извлечь:

-   магазин;
-   дату;
-   итоговую сумму;
-   позиции;
-   количество;
-   цену;
-   скидки.

Но распознанные данные первоначально являются **черновиком**, а не
подтверждённым финансовым фактом.

После подтверждения пользователя они становятся частью предметной
модели.

Это позволяет строить аналитику не только по категории «Питание», но и
по продуктовой корзине:

``` text
молоко
хлеб
овощи
мясо
напитки
...
```

и отслеживать изменение цен и структуры покупок.

------------------------------------------------------------------------

## 13. Категоризация и обучение на подтверждениях

Не следует вызывать LLM для каждой известной операции.

Например, если пользователь несколько раз подтвердил:

``` text
LESTA → Игры
```

Grace должен создать устойчивое правило категоризации.

Пример:

``` text
CategorizationRule
├── pattern
├── category
├── confidence
└── source = user_confirmation
```

Следующая аналогичная операция классифицируется обычным кодом.

Приоритет может выглядеть так:

``` text
explicit user rule
        ↓
known merchant rule
        ↓
deterministic classifier
        ↓
LLM suggestion
        ↓
user confirmation
```

Это повышает предсказуемость и уменьшает стоимость ИИ.

------------------------------------------------------------------------

## 14. Память ассистента

Знания ассистента о финансах пользователя должны храниться в Grace, а не
только в памяти LLM.

Можно разделять:

``` text
FinancialFact
CategorizationRule
UserPreference
MerchantRule
```

Например:

``` json
{
  "pattern": "LESTA",
  "category": "gaming",
  "source": "user_confirmation"
}
```

При смене модели или поставщика Grace не должен терять накопленное
понимание финансов пользователя.

------------------------------------------------------------------------

## 15. Денежные периоды

Календарный месяц --- не единственный полезный период анализа.

Для реального финансового поведения важны:

-   календарный месяц;
-   период между зарплатами;
-   период после аванса;
-   произвольный диапазон;
-   расчётный период кредитной карты;
-   период рассрочки.

Grace должен позволять финансовому ядру работать с такими диапазонами
явно.

Это необходимо для вопросов:

> Куда ушёл аванс?

> Сколько осталось до зарплаты?

> Какие обязательства предстоят до следующего поступления?

------------------------------------------------------------------------

## 16. Денежный поток и обязательства

Grace должен различать:

``` text
Income
Expense
InternalTransfer
DebtPayment
CreditUsage
Refund
```

Перевод между собственными счетами не является расходом.

Погашение задолженности требует отдельной семантики: оно влияет на
денежный поток, но может соответствовать расходам, которые уже были
зафиксированы ранее.

Это необходимо учитывать, чтобы избежать двойного подсчёта.

Обязательства должны моделироваться отдельно от обычных расходов:

``` text
Obligation
├── type
├── total
├── remaining
├── due dates
├── payment schedule
├── grace period
└── status
```

Так Grace сможет прогнозировать будущую доступность денег, а не только
анализировать прошлое.

------------------------------------------------------------------------

## 17. Web-клиент

Существующий подход React + TypeScript и архитектура Feature-Sliced
Design могут быть сохранены.

Ориентировочная структура:

``` text
web/src/
├── app/
├── pages/
├── widgets/
├── features/
├── entities/
└── shared/
    ├── api/
    │   ├── generated/
    │   └── client.ts
    ├── ui/
    └── lib/
```

При этом нельзя переносить финансовые правила в `features` или
`entities` только потому, что их удобно реализовать на клиенте.

Клиент отвечает прежде всего за:

-   отображение;
-   пользовательское взаимодействие;
-   локальное состояние интерфейса;
-   формы;
-   оптимистические обновления там, где они безопасны;
-   работу с Grace API.

------------------------------------------------------------------------

## 18. Нативный iOS-клиент

Архитектура должна позволять позднее создать полноценное нативное
приложение на Swift/SwiftUI без изменения финансового ядра.

iOS-клиент потенциально даст Grace:

-   удобное фотографирование чеков;
-   Face ID;
-   Keychain;
-   push-уведомления;
-   фоновые обновления;
-   widgets;
-   Shortcuts;
-   локальный кэш.

Но iOS остаётся ещё одним клиентом Grace API.

Бизнес-правила не переносятся из Go в Swift.

------------------------------------------------------------------------

## 19. Локальная разработка

После объединения репозитория желательно иметь единый способ запуска:

``` bash
make dev
```

который может поднимать:

``` text
postgres
api
web
```

позднее:

``` text
object storage
```

При этом отдельные компоненты должны оставаться удобными для локальной
разработки.

Например:

``` bash
cd web
npm run dev
```

не должен требовать полной пересборки всего проекта.

------------------------------------------------------------------------

## 20. Что не следует делать на раннем этапе

Не рекомендуется преждевременно вводить:

-   микросервисы;
-   отдельный AI-service;
-   Kafka и другие брокеры без реальной необходимости;
-   сложную событийную инфраструктуру;
-   собственный универсальный framework для агентов;
-   векторную базу «на всякий случай»;
-   сложную систему плагинов;
-   множество уровней абстракции repository/service/usecase без
    практической потребности;
-   общий UI между React и Swift;
-   прямой доступ LLM к PostgreSQL;
-   хранение бизнес-состояния в промптах.

Архитектура должна усложняться вслед за реальными требованиями.

------------------------------------------------------------------------

## 21. Первый вертикальный срез

После объединения репозиториев следующий этап желательно посвятить не
инфраструктуре, а одному полноценному пользовательскому сценарию.

Хороший первый кандидат:

``` text
Account
   ↓
Transaction
   ↓
Category
```

Вертикальный срез должен пройти через всю систему:

``` text
PostgreSQL
    ↓
migration
    ↓
Go domain
    ↓
repository
    ↓
service/use case
    ↓
HTTP API
    ↓
OpenAPI
    ↓
TypeScript client
    ↓
React
```

На этом этапе ИИ не требуется.

Цель --- проверить архитектуру на настоящей предметной задаче.

После этого можно добавить:

``` text
Receipt → ReceiptItems
```

затем:

``` text
Obligation → Payment Schedule
```

и только после появления устойчивого финансового ядра:

``` text
Assistant → Tools → Financial Core
```

------------------------------------------------------------------------

## 22. Grace как живая предметная модель

Разработка Grace может опираться на реальные финансовые сценарии.

Каждый новый случай проходит последовательность:

``` text
реальный финансовый случай
          ↓
понимание его семантики
          ↓
формализация правила
          ↓
изменение предметной модели
          ↓
реализация в Grace
```

Это позволяет избежать проектирования финансового приложения
исключительно по предположениям.

Реальные неоднозначные случаи --- переводы между своими счетами,
погашение задолженности, рассрочки, чеки, остаточные средства,
зарплатные периоды, изменяющиеся расходы на питание --- являются
полезными тестами качества модели.

------------------------------------------------------------------------

## 23. Целевой пользовательский опыт

Grace должен постепенно приблизиться к взаимодействию следующего уровня:

> **Пользователь:** Что произошло с деньгами после аванса?

Grace самостоятельно получает подтверждённые данные и отвечает:

> После поступления аванса основная часть средств была направлена на
> обязательства: погашение задолженности, аренду и ближайшие платежи. На
> повседневные расходы ушло X ₽, из них Y ₽ --- питание. До следующего
> ожидаемого поступления остаётся Z ₽ свободных средств с учётом
> известных обязательств.

И пользователь может продолжить:

> Почему питание получилось таким дорогим?

Grace обращается к детализации чеков и сравнивает период:

> Расходы выросли главным образом из-за увеличения средней стоимости
> одной покупки и нескольких крупных закупок. Наиболее заметно выросли
> такие группы продуктов...

Это принципиально отличается от обычного интерфейса:

``` text
Питание — 18 450 ₽
████████████████ 23%
```

Графики остаются полезны, но Grace должен помогать понимать **причины и
последствия**.

## 24. Итоговая архитектурная формула

Целевую систему можно представить следующим образом:

``` text
                         GRACE

               ┌────── Clients ──────┐
               │                     │
          React Web              SwiftUI iOS
               │                     │
               └─────────┬───────────┘
                         │
                    Grace API
                       Go
                         │
        ┌────────────────┼────────────────┐
        │                │                │
 Financial Domain     Analytics      AI Assistant
        │                │                │
        │                │           tools/context
        │                │                │
        └────────────── Data ─────────────┘
                         │
              ┌──────────┴──────────┐
              │                     │
          PostgreSQL          Object Storage
```

Главное направление зависимостей:

``` text
AI → Grace
```

а не:

``` text
Grace → AI
```

Grace должен оставаться полноценной финансовой системой без языковой
модели.

ИИ превращает эту систему в более удобный, объяснимый и интеллектуальный
инструмент.

## 25. Основной критерий архитектурных решений

При появлении новой функции полезно задавать два вопроса:

1.  **Как Grace представляет и решает эту задачу без ИИ?**
2.  **Как ИИ может сделать взаимодействие с этой возможностью проще и
    полезнее?**

Если ответ на первый вопрос отсутствует и вся логика существует только
внутри промпта, скорее всего, граница ответственности выбрана
неправильно.

Если же Grace обладает структурированной моделью и детерминированными
операциями, ИИ может стать мощным интерфейсом к этой модели, не
превращаясь в её фундамент.

Именно на этом принципе следует строить дальнейшее развитие Grace.
