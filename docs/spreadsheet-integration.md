# Интеграция действующей финансовой таблицы в Grace

Дата анализа: 2026-10-06. Проверенный код: main 249eb2a.

Таблица владельца рассматривается как эталон пользовательских сценариев,
структуры и накопленных свидетельств. Формулы и вручную записанные итоги
проверяются независимо. Значения реальных операций, банковские реквизиты и
файлы документов не включены в этот документ. Подробная построчная сверка
остаётся локальным пользовательским результатом анализа.

Владелец подтвердил: время операций — Asia/Yekaterinburg; дополнительные
записи вне диапазона формул следует разбирать индивидуально.

## Сохранить существующие инварианты

Расход возникает при покупке; погашение основного долга не создаёт второе
потребление. Заёмные поступления и кредитный лимит не являются доходом.
Внутренний перевод требует двух счетов и атомарных проводок. Чек детализирует
покупку без нового списания. Плановый платёж не является состоявшейся
операцией. Финансовая арифметика остаётся в Go/PostgreSQL; LLM не определяет
остатки, даты, дубли или доказанность операции.

## Изменения модели

1. **Происхождение и черновики.** ImportBatch, SourceRecord, ImportIssue,
   DocumentReference и ReconciliationCandidate. Сохранять снимок, оригинальные
   значения/формулы, координаты, классификацию и решение пользователя. Не
   создавать Posting до принятого отдельного контракта публикации.
2. **Три независимых связи.** Ledger Account отражает движение денег;
   PaymentInstrument обозначает карту/стикер; CreditFacility обозначает
   единый кредитный договор. Несколько инструментов могут относиться к одной
   facility и не дублируют её долг. Alias сопоставляет написания в источниках.
3. **Финансирование.** Классификация own/borrowed/unknown и ссылка на facility
   не выводятся только из типа счёта. Заём, поступивший на дебетовый счёт,
   остаётся заёмным источником; смешанное финансирование требует правила
   распределения, которое нельзя придумывать по названию маршрута.
4. **Кредитный снимок.** principalOutstandingMinor, accruedInterestMinor,
   feesMinor, totalDebtMinor, availableLimitMinor, pendingHoldMinor и asOf.
   Неизвестное значение — null, не ноль. Ограничения и банк могут рассчитывать
   доступность лимита по основному долгу, а не всей задолженности.
5. **Графики.** Версионированные DebtSchedule и PaymentRequirement с датой,
   видом требования, суммой и документом. Сумма будущих платежей может
   превышать текущий основной долг; её нельзя записывать в remainingMinor
   текущего Obligation без изменения семантики. Изменения графика сохраняют
   историю, связанные фактические платежи и уже оплаченные части.
6. **Платежи.** Отдельный принятый scope должен определить credit_drawdown,
   погашение/рефинансирование и PaymentAllocation по телу, процентам и
   комиссиям. Нынешний debt_payment списывает деньги с одного счёта; он не
   обновляет автоматически произвольный кредитный договор/кредитный счёт.
7. **Метаданные пользователя.** Подкатегория, приоритет расходов, признак
   регулярности и категория бюджета. Регулярность — подсказка для правила,
   а не команда автоматически создавать будущие финансовые события.
8. **План доходов.** IncomeSchedule, PlannedIncomeOccurrence и календарь
   нерабочих дней. Только подтверждённый income_received меняет остаток.

## Типы данных

| Данные источника | Целевой тип и правило |
| --- | --- |
| Суммы в рублях, числа и текст | int64 minor units + currency=RUB; десятичный разбор без float-арифметики; неоднозначные значения и дроби меньше копейки отклоняются |
| Неизвестный остаток/ставка | nullable поле и статус знания; пустое не равно нулю |
| Дата без времени | LocalDate YYYY-MM-DD и precision=date; не выдумывать час события |
| Время без offset | LocalDateTime + подтверждённая Asia/Yekaterinburg; UTC только после явной конверсии |
| Серийная дата Sheets | Календарная конверсия от 1899-12-30 с сохранением исходного значения и точности |
| Ставка | Decimal/string fixed precision + period/basis + effective dates; число без базы не становится автоматически APR |
| Тип операции | Закрытый enum после явно заданной таблицы соответствий; неизвестный тип остаётся issue |
| Приоритет, регулярность | Enum и nullable boolean; не смешивать приоритет расхода с очередностью погашения долга |
| Название счёта/карты/договора | UUID канонической сущности + подтверждённый alias; строка с цепочкой стрелок — предложение маршрута, не счёт |
| ID и номер строки | Внутренний стабильный UUID + исходный ID; номер строки — координата снимка, не постоянный ключ |
| Формула, статус и итог | Вычисляемая проекция/свидетельство источника; хранить отдельно от факта |

## Обнаруженные риски переноса

- Основной журнал и дополнительный блок за пределами формул частично
  пересекаются; есть совпадения с другими датами. Суммировать оба блока без
  подтверждённой дедупликации нельзя.
- Даты основного журнала — строки; в дополнительном блоке встречаются
  серийные даты. Часть сумм сохранена текстом и пропускается агрегатами Sheets.
- Реальные виды погашений/переводов отличаются от dropdown и критериев
  формул. Обязателен контроль схемы, а не доверие успешному значению ячейки.
- Формулы покупок выписки ищут старое название источника; некоторые выплаты
  имеют сумму в формуле remaining, но не в отдельном поле требования.
- Два платежных идентификатора могут относиться к одному договору; остатки
  разных дат, HOLD и общий долг по нескольким продуктам не взаимозаменяемы.
- Некоторые операции не имеют установленного источника или назначения;
  фиктивный счёт и автоматическая категория не устраняют неопределённость.
- Исторические ставки, условия и графики записаны свободным текстом.
  Автоматическое извлечение создаёт только кандидаты с ссылкой на документ.
- Реестр первичных документов не содержит самих файлов. Его статус
  «Проверено» — утверждение источника, а не результат нового банковского
  сопоставления в Grace.

## Порядок интеграции

Актуальный порядок этапов и уточнённые владельцем требования к банковским PDF,
товарам, временным фото чеков, хранению документов и ролям Jev/LLM описаны в
[roadmap](roadmap.md). Этот анализ фиксирует исходное сопоставление таблицы;
обсуждение требований не является принятием implementation scope.

Следующий предлагаемый work item — [SPEC-0016](specs/0016-spreadsheet-import-review.md):
локальный нормализатор снимка и проверяемый отчёт сверки без изменения ledger.
Это даёт стабильный входной контракт и список нерешённых вопросов до миграции
денег. Затем отдельно принять кредитную модель/финансирование, publication
подтверждённых записей с provenance и UI месячной сводки. План зарплаты,
календарь и пользовательские бюджеты — последующие независимые scope.

## Граница доступа

Таблица только прочитана; финансовое ядро и production не изменялись. Реальные
снимки, операции и первичные документы не коммитить. Будущие данные импорта
обязаны принадлежать owner и сохранять RLS, составные FK, session, CSRF и Origin.
Приложению не нужны credentials Google, использованные оператором для этого
анализа. Онлайн-синхронизация требует отдельного авторизованного контракта.
