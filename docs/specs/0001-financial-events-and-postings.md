## Проблема и пользовательский результат

Текущая покупка одновременно создаёт строку `transactions` и изменяет
`accounts.balance_minor`. Такой остаток может разойтись с историей при
повторной доставке запроса, будущем редактировании или ошибке импорта.

Пользователь должен видеть объяснимый остаток, доходы, покупки и переводы между
своими счетами без двойного учёта расходов.

## Scope

- ввести `FinancialEvent` как финансовый смысл операции;
- ввести одну или несколько `Posting` для движения денег по счетам;
- поддержать `purchase`, `income_received`, `refund`, `debt_payment`;
- поддержать атомарный `internal_transfer` двумя связанными проводками;
- вычислять текущий остаток из начального остатка и проводок;
- добавить защиту от повторной записи одного command;
- обновить PostgreSQL, Go API, OpenAPI, generated TypeScript и React;
- мигрировать данные текущего первого среза без потери операций.

## Non-goals

- редактирование и удаление подтверждённых событий;
- split-категоризация одной покупки;
- перевод между разными валютами и валютная переоценка;
- банковский импорт;
- обязательства и графики платежей;
- авторизация, несколько пользователей и ИИ.

## Текущее поведение и доказательства

- `POST /api/v1/transactions` вставляет операцию и изменяет
  `accounts.balance_minor` в одной DB-транзакции;
- `internal_transfer` намеренно отклоняется;
- web-клиент создаёт только `purchase`;
- balance является изменяемым полем, а не производным read model.

## Предметная модель и инварианты

`FinancialEvent`:

- id;
- kind;
- source;
- category;
- merchant/description;
- occurred_at;
- idempotency_key;
- created_at.

`Posting`:

- id;
- financial_event_id;
- account_id;
- direction: `credit | debit`;
- amount_minor: положительное целое;
- currency;
- created_at.

Инварианты:

1. Сумма проводки всегда больше нуля, валюта указана явно.
2. Покупка и погашение создают одну debit-проводку.
3. Доход и возврат создают одну credit-проводку.
4. Внутренний перевод создаёт ровно две проводки одинаковой суммы и валюты:
   debit источника и credit назначения.
5. Счета перевода различаются.
6. Внутренний перевод не входит в расходы или доходы.
7. Остаток равен `opening_balance + credits - debits`.
8. Одинаковый idempotency key в одной command-boundary не создаёт второе
   событие и вторые проводки.

Это представление финансовой семантики, а не event sourcing.

## API и OpenAPI

Предлагаемый контракт:

- `GET /api/v1/financial-events`;
- `POST /api/v1/financial-events/purchases`;
- `POST /api/v1/financial-events/incomes`;
- `POST /api/v1/financial-events/transfers`;
- `GET /api/v1/accounts` возвращает вычисленный `balanceMinor`.

Каждая изменяющая команда принимает обязательный `Idempotency-Key`.
OpenAPI обновляется до реализации generated TypeScript-клиента.

Совместимость текущего `POST /api/v1/transactions` является открытым
решением этой спецификации.

## Данные, миграция и rollback

Новая миграция должна:

1. переименовать `accounts.balance_minor` в `opening_balance_minor`;
2. создать `financial_events` и `postings`;
3. преобразовать каждую существующую transaction в одно событие и одну
   проводку;
4. проверить равенство старого и вычисленного остатка для каждого счёта;
5. только после успешной проверки прекратить запись в старую таблицу.

Down-миграция разрешена только пока новые виды событий не использованы. Для
среды с такими данными rollback должен завершаться отказом, а не терять
семантику.

## UI

- единая форма выбирает вид: покупка, доход или перевод;
- покупка требует категорию расхода;
- доход допускает категорию дохода;
- перевод требует два разных счёта;
- список показывает вид события и затронутые счета;
- ошибка повторной/конфликтующей команды показывается пользователю явно.

## Ошибки и негативные сценарии

- неизвестный счёт или категория: `422`;
- одинаковые source/destination в переводе: `422`;
- нулевая/отрицательная сумма: `422`;
- валюты счетов не совпадают: `422` до появления FX-модели;
- повтор того же ключа и того же payload: вернуть первоначальный результат;
- тот же ключ с другим payload: `409`;
- частично записанный перевод невозможен.

## Критерии приёмки

- [ ] PostgreSQL-интеграционный тест применяет миграции с нуля.
- [ ] Backfill сохраняет число операций и остаток каждого счёта.
- [ ] Покупка уменьшает вычисленный остаток ровно один раз.
- [ ] Доход увеличивает вычисленный остаток ровно один раз.
- [ ] Перевод изменяет два остатка атомарно и не меняет общий объём средств.
- [ ] Повтор команды с тем же ключом не создаёт дубликат.
- [ ] Конфликт payload для существующего ключа возвращает `409`.
- [ ] API не позволяет одиночную transfer-проводку.
- [ ] OpenAPI и generated TypeScript проходят сборку.
- [ ] React поддерживает три принятых пользовательских сценария.
- [ ] `make test` и `git diff --check` проходят в worktree и после merge.
