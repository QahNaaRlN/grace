## Проблема и пользовательский результат

Единственный разрешённый product-вызов завершён, стоимость известна и settled.
Все девять строк, количества, цены, суммы, продавец, дата, валюта и номер ФД
совпали с заранее снятым эталоном. Строгая сверка 79/80: правильное напечатанное
локальное время модель поместила в issuedAt как HH:MM, без даты и timezone.
Исходный текст содержит это время. Новый платный вызов для исправления не нужен.

Кроме того, бесплатная служебная позиция корректно распознана, но существующие
Go/OpenAPI/SQL инварианты требуют строго положительные цены и суммы каждой
позиции. Это ограничение Grace, не ошибка OCR. Владелец должен иметь возможность
сохранить такой чек целиком, проверив данные и отдельно подтвердив покупку.

## Scope и non-goals

Только детерминированная нормализация draft-кандидата и поддержка нулевых сумм
дочерних ReceiptItem при положительном общем расходе. Используется сохранённый
ответ и исходное фото, без новых provider POST и без новых расходов OpenRouter.
Промпт, schema запроса, модель, canonical, provider, тарифные потолки и routing
не меняются. Финансовое подтверждение остаётся явным; реальные покупки/проводки
в этом пакете не создаются. Нет определения счёта/категории по догадке, удаления
бесплатных строк, вывода timezone по адресу или filename, новой серии экспериментов.

## Текущее поведение

Релиз dab06a9 (PR142) установлен и здоров. Вызов 1/1 consumed, повтор закрыт.
Черновик extracted/revision2 содержит все девять строк; исходное extraction

В UI напечатанное время скрывается за общей подписью «время неизвестно», хотя оно

не предлагает отдельного сохранения без попытки финансового preview.

## Модель и инварианты

R1. Только для AI-originated extracted-кандидата: если issuedDate — корректная
календарная дата, а issuedAt — строго валидное локальное HH:MM либо HH:MM:SS без
timezone, нормализованное draft.fields.issuedAt становится null. Дата сохраняется
точно. Исходные extractions[].fields и sourceText сохраняются неизменными.
Полный RFC3339 timestamp не меняется; неверная дата, неверные часы/минуты/секунды,
отсутствующая дата и конфликт даты с timezone-aware timestamp не угадываются и
остаются ошибкой. Нормализация не применяется к произвольным ручным правкам.

Новые extraction формируют нормализованный кандидат отдельно от original.
Для уже сохранённого extracted-кандидата допустима та же нормализованная read
projection, если поля соответствуют исходному extraction и пользователь ещё не
сохранял собственную правку; read не меняет SQL и revision. Обычное последующее
редактирование сохраняет нормализованные поля по прежнему revision/preview policy.
Валидные старые кандидаты и ранее подтверждённые финансовые записи не меняются.

R2. QuantityMilli >0, unitPriceMinor ≥0, lineTotalMinor ≥0. Общий totalMinor >0,
покупка и проводки имеют строго положительную сумму. Все деньги — integer minor
units с явной валютой, без float. Сумма строк точно равна total. В draft прежняя
проверка quantity × unitPrice − явно указанная скидка = lineTotal сохраняется с
тем же округлением; никакие цены/количества/скидки не придумываются.
Полностью бесплатный чек не создаёт purchase. Отрицательные значения, неверная
арифметика, переполнение и нулевое количество отвергаются. Бесплатные позиции
сохраняются в ReceiptItem; им не создаются отдельные нулевые финансовые события.

R3. Подпись поля — «Дата чека», без ложного утверждения об отсутствии времени.
Исходный sourceText последнего распознавания доступен в компактном read-only
раскрываемом блоке «Исходный текст распознавания». Правки кандидата не меняют этот
блок. JSON/provider protocol в пользовательский поток не выводятся.

## API/OpenAPI

Форма DTO сохраняется: ReceiptDraft.fields — кандидат, extractions — исходные
результаты. Документировать это различие и нормализацию локального clock без
timezone. В ReceiptItem/CreateReceiptItem minimum для unitPriceMinor и
lineTotalMinor меняется с1 на0; quantity и total остаются minimum1. Остальные
денежные контракты, маршруты и confirmation DTO не меняются. После изменения
OpenAPI обязательно regenerate TypeScript; вручную DTO в web не дублировать.

## Данные, миграция и rollback

Новая additive migration ослабляет только два CHECK у receipt_items: цена и
сумма строки ≥0. Receipt total, quantity, FK, owner isolation, immutable confirmed
история и ledger invariants сохраняются. Down отказывается при сохранённых
нулевых позициях, не удаляет и не переписывает их. В таком состоянии сохраняется
совместимая схема/API; rollback не должен разрушать принятую историю.
Нормализация original extraction не переписывает; массовой миграции дат нет.

## Проверки и приёмка

- R1: unit negative controls на local clock + valid date, HH:MM:SS, границы суток,
  неверные дату/clock, missing date, RFC3339 и conflicting date; original immutable.
  SQL/API проверяют новый и уже сохранённый extracted-кандидат, read без SQL-write,
  сохранение правки/preview и неизменность исходного extraction/sourceText.
- R2: unit/SQL — платная строка + бесплатная строка с quantity2, exact positive
  total, подтверждение/replay в изолированной БД. Negative cases: all-free total0,
  negative/overflow amounts, quantity0, arithmetic mismatch, foreign owner, stale
  preview и пропущенное подтверждение. Проверить migration up/down retention gate.
- R3: Web тест блока original sourceText и отсутствия его изменения при правках;
  дата подписана без ложного «время неизвестно».
- R4: private offline replay уже полученного ответа: original79/80 остаётся тем
  же, нормализованный кандидат80/80; все девять строк сохраняются. Synthetic
  account/category используются только в изолированных тестах, не назначаются
  реальному чеку агентом. Не считать replay новым OCR-вызовом или гарантией всех фото.
- R5: make test, git diff --check, go vet, профильная SQL integration, CI,
  Delivery/deploy exact SHA с backup/readiness, post-merge gates.
- R6: production GET/reload уже существующего draft показывает исправленный
  кандидат и original sourceText, provider POST delta0, AI usage delta0,
  financial event/posting/receipt delta0. Реальный финансовый preview/confirmation
  остаётся владельцу после выбора счёта и категории.

## Операторское разрешение после acceptance

Принятие открывает реализацию, тесты, PR/merge/CI/Delivery/deploy и read-only
проверку существующего draft. После успешного replay и SQL gates разрешено
повторно квалифицировать только тот же receipt/model/provider на срок ≤7 дней,
с прежними positive request/image ceilings и свежим metadata proof ≤3GET/≤24ч.
Основание qualification — один проверенный реальный ответ + детерминированный
repair, не универсальное качество всех фото. Автоматическое продление не открыто.
Analysis/statement memberships и общий allowance не меняются. Агенту не разрешён
ни один новый платный POST; обычное последующее действие владельца в продукте
требует прежнего отдельного consent и финансового confirmation.

## Ошибки и открытые решения

Неподходящий clock не нормализуется молча; неверные суммы не исправляются моделью.
Финансовый writer не вызывается без прежних проверок/подтверждения. Unknown bill
по-прежнему удерживает резерв; прошлый известный settlement не переписывается.
R отдельно принят владельцем: расширение decoder и финансовых правил разрешено
только в описанных выше границах, без повторного платного распознавания.
