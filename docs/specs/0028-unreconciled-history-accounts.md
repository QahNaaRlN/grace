## Проблема и пользовательский результат

Владелец поручил закончить перенос истории из таблицы. SPEC-0017/0023/0027
сохраняют исходники, решения и точность дат, однако Account требует числовой
opening balance. Таблица может содержать только часть банковских движений,
а доступный кредитный лимит не является собственными деньгами или начальным
долгом. Историю необходимо загрузить без выдуманных текущих остатков.

## Scope

- Счёт с несверенным остатком и необязательным известным начальным остатком.
- Явная отметка несверенного остатка в списке счетов и аналитике.
- Расходы, доходы, погашения и внутренние переводы из подтверждённого импорта
  сохраняются обычными событиями с provenance SPEC-0017.
- Существующие подтверждённые числа остаются целыми minor units.
- Полная история таблицы переносится после проверки серверного preview;
  неизвестные категории остаются без привязки, исходная категория сохраняется
  в provenance. Карты одного банковского счёта не создают отдельные счета.

## Non-goals

Автоматическая загрузка дополнительных банковских операций, полная кредитная
модель, восстановление неизвестного долга, кредитных лимитов и funding,
изменение существующих событий, автоматическое подтверждение или объединение
кандидатов, обход RLS/Origin/CSRF, доступ к данным других пользователей.

## Текущее поведение и доказательства

Основание: main 254bde9. accounts.CreateRequest требует int64 начального
остатка; Repository.List возвращает opening + postings как текущий остаток.
analytics суммирует все счета без информации о полноте истории. Создание
несверенного счёта сейчас невозможно; ноль выглядел бы проверенным фактом.
Импорт сохраняет funding/subcategory как исходные свидетельства, а не поля
финансового ядра. Это ограничение остаётся явно видимым в preview.

## Предметная модель и инварианты

1. Account хранит openingBalanceMinor как nullable integer и balanceReconciled
   как boolean. Неизвестное значение — null, никогда не подставленный ноль.
2. Сверенный счёт требует известного openingBalanceMinor. Несверенный счёт
   допускает известный или неизвестный opening balance.
3. balanceMinor = null для несверенного счёта. Проводки сохраняются и участвуют
   в статистике операций независимо от известности остатка.
4. Импорт частичной истории создаёт несверенные счета. Числа из выписки
   сохраняются только с конкретным основанием даты/счёта; неизвестный полный
   кредитный долг не заменяется денежным остатком расчётного счёта.
5. Opening/closing балансы валюты в PeriodSummary неизвестны, если есть
   несверенный счёт этой валюты. Суммы операций продолжают считаться точно.
6. LiquidBalance и AvailableAfterObligations неизвестны, если несверен хотя
   бы один ликвидный счёт этой валюты. Суммы обязательств остаются известными.
7. Несверенный кредитный/рассрочный счёт не включается в ликвидные деньги.
8. Date-only остаётся date-only. Дубли и общие итоги чеков исключаются только
   по уже подтверждённым решениям. Заёмное поступление не является доходом.
9. Смена статуса на сверенный после создания не входит в этот этап: для неё
   потребуется отдельная процедура сверки с проверкой покрытия истории.

## API и OpenAPI

CreateAccount: nullable openingBalanceMinor, необязательный balanceReconciled
(по умолчанию true для совместимости). true + null возвращает validation error.
Account: nullable balanceMinor, boolean balanceReconciled.
PeriodSummary: nullable openingBalanceMinor/closingBalanceMinor.
CashPosition: nullable liquidBalanceMinor/availableAfterObligationsMinor.
Пропущенное обязательное поле openingBalanceMinor не считается нулём.
Импорт допускает purchase с неизвестной привязкой категории (categoryId=null),
как предусмотрено Scope; категория источника остаётся в provenance. Ручное
создание purchase сохраняет прежнее требование expense-категории.
Сгенерировать TypeScript из api/openapi.yaml. Финансовые DTO не дублировать.

## Данные, миграция и rollback

Добавить accounts.balance_reconciled DEFAULT true NOT NULL, разрешить NULL
opening_balance_minor, добавить CHECK (NOT balance_reconciled OR
opening_balance_minor IS NOT NULL). Старые счета сохраняют прежнее поведение.
Миграция не меняет postings/events/provenance/owner_id или привязку identity.
Перед выпуском — backup, после — проверка неизменности прежних финансовых
записей. Rollback не подставляет нули: downgrade при новых несверенных счетах
отказывается выполняться; откат приложения требует совместимой версии API.

## UI

В форме создания счёта выбор «Остаток пока не сверён»; начальный остаток
необязателен при этом выборе. При известном числе пояснить дату основания.
Счета и аналитика показывают «Не сверён»/«Неизвестно» вместо денежных нулей.
Импорт продолжает требовать выбор доступного счёта и отдельное подтверждение
серверного предварительного просмотра. Политика SPEC-0017 сохраняется.

## Ошибки и негативные сценарии

- Сверенный счёт с null/пропущенным opening balance отклоняется.
- Невалидные тип/валюта/карта и межпользовательские ссылки отклоняются.
- Неизвестный баланс не форматируется как 0 и не участвует в доступных деньгах.
- Повтор подтверждения импорта не создаёт повторных событий.
- Неполная история не выдаётся за подтверждённый банковский остаток.

## Критерии приёмки

- [ ] AC1. Несверенный счёт создаётся с null или известным начальным остатком;
  после проводок balanceMinor остаётся null.
- [ ] AC2. Старые сверенные счета и арифметика дают прежние результаты.
- [ ] AC3. Смешанная аналитика сохраняет суммы операций и возвращает null
  для недоказанных балансов; кредитные счета не становятся ликвидными.
- [ ] AC4. UI формы/счетов/обзора/ассистента честно отображает неизвестность.
- [ ] AC5. API/types, RLS и финансовая изоляция проверены; миграция не меняет
  события, проводки и provenance.
- [ ] AC6. История загружается через сохранённые решения и серверный preview;
  итоговые события совпадают с выбранными строками, source evidence сохранены.
