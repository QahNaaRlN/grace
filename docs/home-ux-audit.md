# UX/UI-аудит главной страницы Grace

Дата: 2026-10-06. Запрос владельца — осмотр и анализ перед переработкой дизайна.
Это эвристический аудит, не реализация и не исследование с реальными участниками.

## Главный вывод

Существующая визуальная система цельная, но главная объединяет обзор,
подробную аналитику, две постоянно раскрытые формы и полный журнал. Первый
экран занят описанием продукта и карточками счетов. Быстрый ввод, остаток после
известных платежей и просрочки требуют прокрутки. Главную следует организовать
вокруг вопросов «что сейчас», «что требует внимания» и «что сделать».

Два наиболее срочных дефекта — отсутствие пути создать первый счёт в пустом
аккаунте и общий статус «Данные актуальны» при недоступной аналитике.

## Как проводилась проверка

- Проверен main-код с integrated SPEC-0010 и SPEC-0018, baseline origin/main
  57f47ae. SPEC-0017 review branch не используется как deployed baseline.
- Production в доступном Chrome открыл экран входа, а не финансовую главную.
  Новый Telegram login ради аудита не запускался. Проверена неизменённая Web
  сборка текущего main в локальном браузере с read-only synthetic API.
- Ни реальных финансовых данных, ни invitations/credentials в fixture нет.
  API fixture допускает только GET/HEAD; действия записи блокируются.
- Chrome desktop: 1280×900. Responsive widths: 390×844 и 320×740 CSS px;
  content width 1265/375/305 из-за scrollbar. Это desktop-browser emulation,
  не проверка настоящей мобильной клавиатуры, Telegram WebView или screen reader.
- Сценарии: normal (3 accounts/5 events), empty, analytics error, long name/
  safe-integer amount, 40 events. Проверены DOM/AX, layout, focus и screenshots.
- Мобильная normal страница: высота 5393 px, 17 полей/селектов. Секция ввода
  начинается на y=2347, save event — y=3042, подробности — y=3979. На desktop
  ввод начинается на y=1244, save event — y=1755. Это измерения конкретной fixture,
  а не оценка времени выполнения задачи или статистика реальных пользователей.
- При 40 событиях мобильная страница выросла до 8872 px.

## Что уже работает хорошо

Единый shadcn/ui/Radix стек, спокойная узнаваемая палитра, согласованные
скругления и отступы. На normal ширине 390 нет горизонтального overflow.
Основные inputs/save buttons — 44 px; навигация закреплена снизу и учитывает
safe-area. Суммы форматируются по валюте, направления имеют знак/текст, перевод
получает отдельную иконку. Focus date input виден. Состав чека открывается по
запросу через Dialog: этот существующий pattern полезен и для других действий.

Система не требует замены библиотеки или полного отказа от визуального бренда.

## Предлагаемая иерархия новой главной

1. Компактный header: «Обзор», выбранная валюта при необходимости, актуальность
   конкретных данных и доступная primary action «Добавить операцию».
2. Одна доминирующая финансовая сумма: остаток после известных платежей,
   с выбранным горизонтом и источником. Рядом/ниже — текущий ликвидный остаток.
   Это не обещание «можно потратить», прогноз доходов или банковский лимит.
3. «Требует внимания»: просроченные и ближайшие известные платежи с датами,
   текстовым статусом и понятным переходом в детали. Нулевая просрочка не
   превращается в выдуманный финансовый score.
4. Последние операции: merchant/description, дата, счёт, сумма/валюта/направление,
   доступ к деталям и ко всем операциям.
5. Счета компактным обзором, без одинаково крупных декоративных карточек на
   каждый счёт; больше пространства — только нужным цифрам.
6. Подробная аналитика и формы открываются по задаче. На desktop можно иметь
   основную колонку обзора/операций и вторую колонку платежей; порядок смысла
   сохраняется на mobile. Текущие Dialog primitives можно использовать повторно.

Сохранить собственную финансовую модель: все денежные итоги от Go API,
валюты отдельно, фактические операции отдельно от планов. UI может форматировать
и выбирать отображение, но не изобретать новые финансовые вычисления/прогнозы.
Не суммировать credit balances, liquid cash и разные валюты под одной подписью.

## Лучшие практики и применение

- Progressive disclosure: частые действия и важные состояния видны сразу,
  редкие параметры/полные таблицы раскрываются по контексту. Это не сокрытие
  важных сумм, дат или условий расчёта. [NN/g](https://www.nngroup.com/articles/progressive-disclosure/).
- Видимая иерархия: один основной focal point вместо равноценных hero, трёх
  зелёных cards и нескольких больших форм. Цвет и размеры отражают задачи,
  отрицательные/просроченные состояния имеют текст, а не только оттенок.
- Состояния: loading skeletons/стабильное место блоков, empty с следующим
  действием, partial errors и retry рядом с affected block. CLS не измерялся;
  placeholder layout предложен для проверки, а не объявлен performance fix.
- Accessibility: обычный текст ≥4.5:1, крупный ≥3:1; формы с labels, логическая
  heading hierarchy, visible focus, keyboard dialog focus/Esc/return, reflow без
  потери информации. [W3C contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
- Target size: проектные 44px для primary controls; WCAG AA 24px/spacing не
  смешивать с этим стандартом. [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).
- Period selection: «Этот месяц», «Прошлый месяц», «Свои даты» с понятным
  интервалом. UI labels и преобразование границ должны сохранять текущие API
  exclusive/inclusive semantics и timezone, не менять финансовые правила молча.

## Этапы переработки

Этап 1: исправить H01/H02, поднять primary action/known payments, убрать
постоянно открытые формы из обзора, упростить copy и проверку длинных значений.
Это может использовать существующие accounts/analytics/event contracts.

Этап 2: отдельные задачи полноценного журнала, поиска/filters/paging и деталей,
управления счетами/платежами и ввода прошлой даты. Проверить новые routes/API
потребности и принять scope до реализации.

Этап 3: графики тренда, бюджет/прогноз/credit score только с отдельными данными
и принятыми финансовыми спецификациями. Не рисовать красивые неподтверждённые
графики на основании одного period total. Новая библиотека не нужна для начала.

## Проверка будущего прототипа

- На normal 390×844 primary action и сумма с горизонтом видны без прокрутки;
  полезная информация имеет приоритет над маркетинговым описанием.
- В empty пользователь сразу видит «Добавить первый счёт» и понятную последовательность.
- Сломать только analytics endpoint: affected block/общий статус согласованы,
  успешные данные остаются доступны, retry не запускает финансовую запись.
- На 320px и при zoom/reflow суммы/названия/ошибки не теряются; проверить
  keyboard на реальном Android/iOS, safe-area и устойчивость bottom nav.
- Проверить negative/zero, несколько валют, просрочки, длинный журнал и loading.
- Модальные формы: focus trap, Esc/back, возврат focus, validation, pending,
  lost response и сохранность пользовательского ввода; writes только явно.
- Небольшие пользовательские задания: назвать сумму и горизонт, найти просрочку,
  начать ввод покупки, найти вчерашнюю операцию. Измерять успех/ошибки/время;
  никаких заявлений о проценте улучшения без такого исследования.
