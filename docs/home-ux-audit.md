# UX/UI-аудит главной страницы Grace

Дата: 2026-10-06. Запрос владельца — осмотр и анализ перед переработкой дизайна.
Это эвристический аудит, не реализация и не исследование с реальными участниками.

## Главный вывод

Существующая визуальная система цельная, но главная объединяет обзор,
подробную аналитику, две постоянно раскрытые формы и полный журнал. Первый
экран занят описанием продукта и карточками счетов. Быстрый ввод, остаток после
известных платежей и просрочки требуют прокрутки. Главную следует организовать
вокруг вопросов «что сейчас», «что требует внимания» и «что сделать».

Два наиболее срочных дефекта — отсутствие пути создать первый счёт в пустом
аккаунте и общий статус «Данные актуальны» при недоступной аналитике.

## Как проводилась проверка

- Проверен main-код с integrated SPEC-0010 и SPEC-0018, baseline origin/main
  57f47ae. SPEC-0017 review branch не используется как deployed baseline.
- Production в доступном Chrome открыл экран входа, а не финансовую главную.
  Новый Telegram login ради аудита не запускался. Проверена неизменённая Web
  сборка текущего main в локальном браузере с read-only synthetic API.
- Ни реальных финансовых данных, ни invitations/credentials в fixture нет.
  API fixture допускает только GET/HEAD; действия записи блокируются.
- Chrome desktop: 1280×900. Responsive widths: 390×844 и 320×740 CSS px;
  content width 1265/375/305 из-за scrollbar. Это desktop-browser emulation,
  не проверка настоящей мобильной клавиатуры, Telegram WebView или screen reader.
- Сценарии: normal (3 accounts/5 events), empty, analytics error, long name/
  safe-integer amount, 40 events. Проверены DOM/AX, layout, focus и screenshots.
- Мобильная normal страница: высота 5393 px, 17 полей/селектов. Секция ввода
  начинается на y=2347, save event — y=3042, подробности — y=3979. На desktop
  ввод начинается на y=1244, save event — y=1755. Это измерения конкретной fixture,
  а не оценка времени выполнения задачи или статистика реальных пользователей.
- При 40 событиях мобильная страница выросла до 8872 px.

## Что уже работает хорошо

Единый shadcn/ui/Radix стек, спокойная узнаваемая палитра, согласованные
скругления и отступы. На normal ширине 390 нет горизонтального overflow.
Основные inputs/save buttons — 44 px; навигация закреплена снизу и учитывает
safe-area. Суммы форматируются по валюте, направления имеют знак/текст, перевод
получает отдельную иконку. Focus date input виден. Состав чека открывается по
запросу через Dialog: этот существующий pattern полезен и для других действий.

Система не требует замены библиотеки или полного отказа от визуального бренда.

## Предлагаемая иерархия новой главной

1. Компактный header: «Обзор», выбранная валюта при необходимости, актуальность
   конкретных данных и доступная primary action «Добавить операцию».
2. Одна доминирующая финансовая сумма: остаток после известных платежей,
   с выбранным горизонтом и источником. Рядом/ниже — текущий ликвидный остаток.
   Это не обещание «можно потратить», прогноз доходов или банковский лимит.
3. «Требует внимания»: просроченные и ближайшие известные платежи с датами,
   текстовым статусом и понятным переходом в детали. Нулевая просрочка не
   превращается в выдуманный финансовый score.
4. Последние операции: merchant/description, дата, счёт, сумма/валюта/направление,
   доступ к деталям и ко всем операциям.
5. Счета компактным обзором, без одинаково крупных декоративных карточек на
   каждый счёт; больше пространства — только нужным цифрам.
6. Подробная аналитика и формы открываются по задаче. На desktop можно иметь
   основную колонку обзора/операций и вторую колонку платежей; порядок смысла
   сохраняется на mobile. Текущие Dialog primitives можно использовать повторно.

Сохранить собственную финансовую модель: все денежные итоги от Go API,
валюты отдельно, фактические операции отдельно от планов. UI может форматировать
и выбирать отображение, но не изобретать новые финансовые вычисления/прогнозы.
Не суммировать credit balances, liquid cash и разные валюты под одной подписью.

## Лучшие практики и применение

- Progressive disclosure: частые действия и важные состояния видны сразу,
  редкие параметры/полные таблицы раскрываются по контексту. Это не сокрытие
  важных сумм, дат или условий расчёта. [NN/g](https://www.nngroup.com/articles/progressive-disclosure/).
- Видимая иерархия: один основной focal point вместо равноценных hero, трёх
  зелёных cards и нескольких больших форм. Цвет и размеры отражают задачи,
  отрицательные/просроченные состояния имеют текст, а не только оттенок.
- Состояния: loading skeletons/стабильное место блоков, empty с следующим
  действием, partial errors и retry рядом с affected block. CLS не измерялся;
  placeholder layout предложен для проверки, а не объявлен performance fix.
- Accessibility: обычный текст ≥4.5:1, крупный ≥3:1; формы с labels, логическая
  heading hierarchy, visible focus, keyboard dialog focus/Esc/return, reflow без
  потери информации. [W3C contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
- Target size: проектные 44px для primary controls; WCAG AA 24px/spacing не
  смешивать с этим стандартом. [W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).
- Period selection: «Этот месяц», «Прошлый месяц», «Свои даты» с понятным
  интервалом. UI labels и преобразование границ должны сохранять текущие API
  exclusive/inclusive semantics и timezone, не менять финансовые правила молча.

### Палитра и распределение цвета

Сейчас зелёный используется для бренда, градиентного фона, всех счетов,
акцентов, доходов и части статусов. Одинаковая насыщенность делает разные
смыслы визуально равными. Декоративные hero/карточки конкурируют с цифрами.
Сохраняем зелёный как узнаваемый цвет Grace, уменьшаем площадь насыщенных
заливок, используем нейтральные поверхности и отдельные смысловые токены.

| Роль | Предложение light theme | Применение |
| --- | --- | --- |
| Фон | `#F6F8F7` | Спокойный фон без общего декоративного градиента |
| Поверхность | `#FFFFFF` | Счета, операции, платежи; разделение отступами и границей |
| Основной текст | `#172A24` | Названия, суммы, основной текст |
| Вторичный текст | `#52635B` | Даты, подписи, пояснения; без прозрачности текста |
| Граница | `#DCE5DF` | Декоративное разделение, не единственный признак поля/состояния |
| Бренд / primary | `#16634B`, белый текст | Основная кнопка и выбранный раздел |
| Мягкий акцент | `#E9F4EE`, текст `#16634B` | Активный пункт, небольшая метка |
| Подтверждено / доход | `#166534` на `#F0FDF4` | Успех и поступление с текстом/знаком |
| Внимание | `#92400E` на `#FFFBEB` | Требующий внимания срок, с датой и причиной |
| Ошибка / просрочено | `#B91C1C` на `#FEF2F2` | Ошибка или известная просрочка, явно подписанная |
| Информация / перевод | `#1D4ED8` на `#EFF6FF` или основной текст | Нейтральный перевод, помощь |

Это стартовые sRGB значения для макета, не сертификат контраста всех состояний.
Для каждого сочетания проверить normal/hover/pressed/focus/disabled и реальные
подложки. Светлая граница выше не предназначена как единственная граница
интерактивного поля; для неё нужен отдельный контрастный control token.
Обычный текст — минимум 4.5:1, крупный — 3:1. Цвет не должен быть единственным
носителем информации: нужны подписи, знаки и/или иконки.
[Контраст](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html),
[использование цвета](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).

Расход — обычный текст со знаком и типом операции; красный не требуется для
каждой покупки. Кредитный долг — явно названная задолженность, нейтральная
карточка; красный появляется при проблемном состоянии, а не самом наличии
кредита. Собственный перевод не маркируется как убыток. Главная сумма может
получить одну мягко выделенную поверхность, остальные счета — компактные белые.
Графики, если появятся на реальных данных, используют отдельную категориальную
палитру с подписями; warning/error цвета не превращаются в случайные категории.
Dark CSS существует, но это не доказательство готовности тёмной темы: отдельно
проверить текущие hard-coded white/emerald/red classes перед её публикацией.

### Иконки

Lucide уже используется: замена набора не требуется. Ввести единый словарь
значений и размеров; не менять иконку одной задачи между экраном и меню.

| Смысл | Предлагаемая Lucide иконка | Подпись |
| --- | --- | --- |
| Обзор | `LayoutDashboard` | Обзор |
| Счета | `WalletCards` | Счета |
| Операции | `ListOrdered` | Операции |
| Добавление | `Plus` | Добавить операцию |
| Платежи | `CalendarClock` | Платежи |
| Перевод | `ArrowRightLeft` | Перевод |
| Импорт | `FileInput` | Импорт — после публикации соответствующей функции |
| Ассистент | `Bot` | Ассистент |
| Дополнительное меню | `Menu` | Меню |
| Настройки | `Settings` | Настройки — только при наличии экрана |

Основные иконки 20–24 px, внутри компактной строки 16–20 px; одинаковый stroke
около 2. Это проектная настройка, не требование WCAG. Размер рисунка не равен
размеру зоны нажатия: основные кнопки минимум 44×44 px. Навигация всегда с
видимой подписью. Icon-only close/menu получают доступное имя. Декоративные
SVG скрываются от screen reader. Selected state — фон/индикатор плюс подпись
и семантическое состояние, не только изменение цвета.

HeartPulse допустим как брендовый знак, но не означает рассчитанный health
score. Sparkles в hero не сообщает полезное состояние и может быть убран;
не использовать его как обещание AI там, где отображаются обычные расчёты.

### Мобильная навигация и бургер

В текущем main есть два видимых нижних пункта «Финансы» и «Ассистент», бургер
отсутствует. Поэтому это проектирование расширения навигации, а не исправление
существующего burger-компонента. Скрывать все разделы за бургером не предлагается:
в исследовании NN/g скрытая навигация обнаруживалась хуже смешанной. Это
ориентир, а не замер Grace и не обещание конкретного процента улучшения.
[Исследование NN/g](https://www.nngroup.com/articles/hamburger-menus/).

Предпочтительная целевая схема: нижняя панель «Обзор · Операции · Платежи»;
сверху компактные Grace/название экрана и кнопка «Меню» с burger. «Добавить
операцию» — отдельная видимая кнопка в обзоре, а не навигационная вкладка.
Три нижних пункта предполагают реальные экраны/маршруты: пока их нет, сохранить
текущие доступные разделы, не рисовать недействующие вкладки. Приоритет платежей
против счетов уточнить на пользовательских заданиях будущего прототипа.

Меню открывает боковую панель со счетами, подробной аналитикой, ассистентом,
импортом, доступом/профилем и выходом — только реализованные и разрешённые
пользователю пункты. Управление приглашениями остаётся доступным только роли,
которой оно разрешено; обычные финансовые разделы не получают admin-привилегий.
Не дублировать то же «Меню» одновременно сверху и снизу. Закрытие явной
кнопкой, Esc и backdrop; возврат focus, корректное объявление диалога,
блокировка фонового взаимодействия, видимый текущий раздел. Проверить Back на
реальных mobile browsers и сохранность незавершённого ввода. Нижняя панель
учитывает safe-area и не перекрывает последнюю запись или форму с клавиатурой.
Desktop — видимые пункты в header/компактной боковой навигации, без обязательного
скрытия всех пунктов под burger. Использовать существующие Radix primitives.

### Типографика

В CSS указан `Inter`, но поиск по Web не обнаружил загрузки font files,
`@font-face` или font provider. Поэтому Inter используется лишь если доступен
на устройстве; иначе системный fallback. Это разница между заявленным шрифтом
и гарантированным видом, не доказательство плохого рендера на всех устройствах.

Для первого макета выбрать честный `system-ui` stack: хорошие нативные шрифты,
кириллица и отсутствие дополнительной загрузки. Если нужен одинаковый брендовый
вид, отдельно выбрать self-hosted Inter с кириллицей и проверить лицензию,
font-display, fallback/сдвиги и tabular figures. Не подключать внешний font
provider только ради визуальной единообразности. Одна гарнитура достаточна.

| Роль | Размер / line-height в макете | Вес |
| --- | --- | --- |
| Главная сумма | 32/40 mobile, 40/48 desktop; адаптация длинного значения | 600 |
| Название страницы | 24/32 mobile, 28/36 desktop | 600 |
| Заголовок секции | 18–20/28 | 600 |
| Основной текст, поля | 16/24 | 400 |
| Кнопки | 15–16/22–24 | 500–600 |
| Дата, вторичная подпись | 14/20 | 400–500 |
| Метка нижней навигации | 12–13/16–18 | 500; только короткое название |

Не использовать 12px для сумм, ошибок или существенных условий расчёта.
В финансовых колонках включить tabular-nums, выровнять суммы вправо,
сохранять знак и валюту. Главные числа — обычный tracking; убрать чрезмерно
плотный tracking у длинных сумм. Не обрезать деньги многоточием: разрешать
больше места/адаптацию размера, сохраняя все цифры и удобную читаемость.
Длинные названия могут переноситься; полное название доступно в деталях.
Оставить один h1, последовательные h2/h3, убрать из обзора повторяющиеся
надзаголовки «Сейчас/Понимание/Новое», если они не добавляют смысла.

Проверить увеличение текста, 320px reflow и пользовательские межстрочные/
межбуквенные интервалы без потери информации. WCAG Text Spacing требует
устойчивости к переопределению интервалов пользователем, а не назначения всех
перечисленных в стандарте значений в базовом дизайне.
[W3C Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html).

### Что включить в следующий макет и спецификацию

Один согласованный mobile/desktop вариант: нейтральные поверхности, зелёный
акцент, иерархия сумм и действий, единый словарь иконок, нижние основные
разделы и дополнительное burger-меню. Варианты состояний: пустой аккаунт,
обычный обзор, просрочка, частичная ошибка, длинные суммы и открытое меню.
Проверить контраст реального макета, keyboard/focus, реальные телефоны и
задачи поиска операции/платежа до принятия production-реализации. Маршруты,
управление первым счётом и формы входят в спецификацию как поведение;
смена цветов и гарнитуры сама по себе их не реализует.
