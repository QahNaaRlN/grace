## Текущие возможности и ограничения

- Go/PostgreSQL хранят финансовые факты и выполняют расчёты без LLM.
  Переводы между собственными счетами отделены от расходов, чеки и settlement
  не создают повторных проводок. Деньги хранятся в integer minor units
  с явной валютой.
- Web позволяет вводить покупки, доходы, переводы и платежи по обязательствам,
  подтверждённые чеки и фиксированные обязательства. Возвраты доступны через
  API; отдельной формы возврата пока нет.
- Аналитика поддерживает явный период, категории расходов и доступные
  ликвидные средства после известных обязательств. Валюты не суммируются
  через скрытую конвертацию. Будущие доходы и расходы не прогнозируются.
- Ассистент выбирает один из шести tools: `get_accounts`, `get_period_summary`,
  `get_cash_position`, `get_obligations`, `get_receipts`,
  `get_period_since_income`. Router выключен по умолчанию и в production.
  TypeSafe получает запрос, язык и reference time; финансовые записи и
  результаты tools ему не отправляются. Истории диалога и генеративных
  финансовых объяснений нет.
- Telegram-вход по приглашениям, admin/member и изоляция данных работают в production; первый вход владельца подтверждён. По умолчанию без конфигурации API закрыт (`locked`). Basic Auth сохраняется как внешняя защита. Резервные копии
  находятся на том же VPS; off-site backup не реализован.

## Оставшиеся направления

Это кандидаты из видения, а не принятые work items. Порядок строк не задаёт
приоритет или сроки. Перед реализацией каждого направления требуется отдельная
спецификация и явное принятие владельцем по [spec-first процессу](specs/README.md).

| Направление | Что остаётся сделать | Зависимости и границы |
| --- | --- | --- |
| Независимый вход и восстановление | Passkeys или второй провайдер, безопасное восстановление и управление identity | Telegram-вход уже реализован; внешние аккаунты нельзя автоматически связывать по username |
| Распознавание чеков | Фото, object storage, извлечение данных, `ReceiptDraft`, подтверждение | Подтверждённые чеки уже есть; черновик не должен становиться финансовым фактом без подтверждения |
| Категоризация и память правил | `CategorizationRule`, `MerchantRule`, предпочтения и использование подтверждений | Категории уже есть; известные правила должны работать детерминированно |
| Расширение аналитики | Сравнение периодов, цен и продуктовой корзины, подтверждённые факторы изменения расходов | Детализация чеков есть; нужна отдельная семантика сравнения и сопоставления позиций |
| Обязательства и будущая доступность денег | Повторяющиеся счета, подписки, ожидаемые доходы, кредитные периоды, проценты и grace period | Текущая модель ограничена фиксированным конечным графиком; прогноз нельзя выдавать за подтверждённый факт |
| Объяснения и диалог | Связные ответы, несколько источников, продолжение разговора | Текущий router выполняет один read-only tool; Jev не генерирует объяснения |
| Изменяющие инструменты ассистента | Подтверждение команд и безопасное изменение финансовых данных | Нужна отдельно принятая политика подтверждений; текущие tools доступны только для чтения |
| Нативный iOS-клиент | SwiftUI, фото чеков, локальный кэш и возможности платформы | Клиент должен использовать Grace API и сохранять финансовые правила в Go |

Целевой сценарий «куда ушёл аванс?» → «почему питание подорожало?» из
раздела 23 видения пока не реализован целиком. Подтверждённый доход, сводка
периода, обязательства и позиции чеков уже доступны; объяснение причин,
сравнение корзины, продолжение диалога и прогноз до следующего дохода остаются
будущими возможностями.

## Как поддерживать документ

После интеграции новой спецификации обновить таблицу завершённых этапов,
границы возможностей и соответствующее оставшееся направление. Статус
подтверждать спецификацией, кодом и итоговым evidence, а не только наличием
каталога или draft. Исторические решения, спецификации и отчёты сохранять;
их исходные наблюдения не считать описанием текущей версии.
