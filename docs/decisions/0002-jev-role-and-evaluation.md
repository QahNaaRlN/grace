# Decision 0002: роль Jev и проверка применимости

- Статус: accepted
- Дата: 2026-10-04
- Владелец решения: owner
- Основание принятия: явное согласие owner в Codex-чате, 2026-10-04

## Контекст

Grace должен понимать естественный язык и финансовый смысл данных, но не
может передавать модели владение финансовым состоянием, арифметикой или
разрешением на изменение данных. Финансовое ядро уже предоставляет ассистенту
пять строгих read-only инструментов, однако provider и измеренная политика
маршрутизации пока отсутствуют.

Jev — System One модель TypeSafe AI. Она принимает текстовое или
структурированное состояние и возвращает типизированные ответы:

- `Choice` — выбор одного варианта и распределение вероятностей;
- `Noul` — вероятность ответа «да»;
- `Score` — положение на заданной порядковой шкале.

Jev не генерирует пользовательский текст, не выполняет финансовую арифметику и
не принимает изображения. Confidence описывает концентрацию распределения
ответа, а не истинность результата и не разрешение выполнить действие.

Актуальные внешние контракты:

- [System One](https://docs.typesafe.ai/concepts/system-one);
- [HTTP API](https://docs.typesafe.ai/api);
- [модели и ограничения](https://docs.typesafe.ai/models);
- [confidence](https://docs.typesafe.ai/confidence);
- [intent routing](https://docs.typesafe.ai/patterns/intent-routing);
- [извлечение дат](https://docs.typesafe.ai/cookbooks/date_extraction_cookbook);
- [обработка данных](https://docs.typesafe.ai/legal).

## Решение

Jev рассматривается как опциональный provider узких семантических решений.
Grace сохраняет управление workflow, проверяет ответы модели и вызывает только
явно разрешённые предметные возможности.

Целевое направление зависимостей:

```text
Web / iOS
    ↓
Grace API
    ↓
assistant orchestrator
    ├── deterministic policy and fallback
    ├── Jev semantic judgments
    └── optional generative explanation provider
              ↓
        assistant.Executor
              ↓
        financial modules
              ↓
          PostgreSQL
```

Jev не является заменой генеративной модели. Он может выбрать инструмент,
кандидата, класс или степень релевантности; пользовательское объяснение
формируется детерминированным шаблоном либо отдельным generative provider.

## Разрешённые классы решений

### Первый приоритет

1. Маршрутизация пользовательского запроса в один из read-only инструментов
   ассистента, `clarify` или `unsupported`.
2. Распознавание формы финансового периода и явно названных частей даты.
   Конкретные календарные границы вычисляет и валидирует Go-код.
3. Проверка соответствия предложенного tool call исходному запросу.
4. Выбор между детерминированным обработчиком, generative provider и запросом
   уточнения.

### Экспериментальные кандидаты

Эти сценарии требуют отдельных принятых спецификаций и предметных наборов
данных:

- предложение категории из переданного списка существующих категорий;
- предложение финансового смысла импортированной банковской строки;
- сопоставление merchant с переданным набором кандидатов;
- выбор даты, суммы или позиции из результатов OCR/парсинга;
- оценка семантического сходства кандидатов регулярного платежа;
- ранжирование подтверждённых финансовых событий по необходимости внимания;
- выбор подтверждённых факторов для последующего объяснения.

Модель должна выбирать из кандидатов, найденных кодом, когда это возможно.
Отсутствующий кандидат нельзя заменять сгенерированным значением.

## Запрещённые области ответственности

Jev не используется для:

- расчёта balance, cash flow, period summary, schedule state или обязательств;
- формирования бухгалтерских проводок;
- проверки валютной и денежной арифметики;
- OCR или анализа изображения чека;
- хранения финансового состояния или памяти пользователя;
- прямого чтения PostgreSQL;
- авторизации, аутентификации или multi-user isolation;
- выдачи разрешения на AI-originated write;
- замены Idempotency-Key и серверной валидации;
- автономного изменения категории, события, чека или обязательства;
- генерации финансового совета или свободного пользовательского объяснения.

Высокий confidence никогда не отменяет подтверждение пользователя, если оно
требуется политикой изменения данных.

## Политика неопределённости

Каждый workflow определяет собственную политику обработки результата:

```text
typed answer + probabilities
            ↓
domain-specific threshold
    ├── accept a reversible read-only route
    ├── ask the user to clarify
    ├── send a suggestion for confirmation
    └── abstain / deterministic fallback
```

Порог из документации или демонстрации нельзя переносить в Grace без проверки.
Для write-предложений и финансовой семантики допустимая ошибка строже, чем для
безопасного read-only выбора представления.

## Данные и приватность

1. Provider получает минимально необходимое состояние, а не всю финансовую
   историю.
2. Первый benchmark использует только синтетические или необратимо
   обезличенные примеры.
3. API key хранится только на сервере или в локальном окружении evaluator и не
   попадает в React, fixtures, логи или отчёты.
4. До production-передачи пользовательских финансовых данных владелец должен
   отдельно принять retention/DPA/региональные условия. Заявление поставщика об
   отсутствии обучения на customer data не эквивалентно zero data retention;
   ZDR заявлен поставщиком как enterprise-возможность.
5. Сырые provider request/response с пользовательскими данными по умолчанию не
   журналируются.

## Язык, версия модели и воспроизводимость

- Основной evaluation corpus — русский язык; английские примеры служат только
  контрольной группой.
- Для benchmark используется явный versioned model id, а не плавающий alias.
- Отчёт сохраняет фактический model id из ответа, версию набора данных, версию
  вопросов и параметры запуска.
- После смены модели или формулировок вопросов benchmark выполняется заново.
- Типизированный ответ гарантирует форму интерфейса, но не правильность вывода.

## Отказоустойчивость

Grace остаётся работоспособным без Jev. Timeout, rate limit, overload,
невалидный ответ и отсутствие credentials превращаются в типизированную ошибку
provider и приводят к безопасному fallback, а не к частичному финансовому
результату или скрытой записи.

## Следствия

- Первый шаг — SPEC-0006 с evaluation harness, а не production chat.
- Интеграция остаётся внутри модульного Go backend; отдельный AI-service пока
  не вводится.
- Provider boundary не импортируется финансовыми модулями.
- Категоризация, ReceiptDraft, write tools и generative explanations остаются
  отдельными будущими спецификациями.
- Production routing разрешается только после принятия отдельной спецификации
  с измеренными порогами и fallback-поведением.

## Условия принятия решения

Owner принимает или изменяет:

1. роль Jev как optional semantic-decision provider;
2. перечень запрещённых областей ответственности;
3. обязательный русскоязычный benchmark до production-интеграции;
4. необходимость отдельного privacy gate до передачи реальных финансовых
   данных;
5. разделение evaluation, read-only routing и AI-originated writes на разные
   спецификации.


## Уточнение фактов о capabilities — 2026-10-18

Исходное утверждение выше «не принимает изображения» отражает момент принятия
решения, а не текущую границу внешнего API. По актуальной первичной документации
[TypeSafe Images](https://docs.typesafe.ai/images) Jev 1.13/1.14 имеют
экспериментальный image input, а Box — Jev 1.14. Эти возможности обозначены
провайдером как не готовые к production и требуют opt-in. Это уточнение факта
не разрешает включать их в Grace, отправлять личные изображения или менять
принятые privacy/confirmation gates.

[accepted SPEC-0055](../specs/0055-bank-statement-pdf-import.md) рассматривает только
текстовый input: LLM предлагает структуру банковской выписки; Jev может выбирать
из найденных spans и проверять узкие интерпретации после отдельного измерения.
[Pre-parsed value extraction](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook)
и [SDE cascade](https://docs.typesafe.ai/cookbooks/sde_cascade) показывают эти разные
роли, но их demo thresholds/качество не являются acceptance evidence Grace.
Финансовая арифметика, source validation и подтверждение записи остаются в Grace.

По поручению владельца сменить курс подготовлен [S1.22 V1–V3](../specs/0055-s122-direct-page-reading.md),
**proposed / implementation not_started**. Один research candidate получает PNG+text
и возвращает строки+quotes; Go выполняет binding/grounding/арифметику/financial guards.
Предлагается OpenAI Responses/gpt-6-astra, доступ/качество/region/funding UNVERIFIED.
Это не Jev vision и не переключение production provider. После принятия возможна
только offline-реализация перечисленного source/fakes; paid V4/key setup/merge/deploy
отдельно. Историческое принятое решение выше сохраняется; production image non-goal
SPEC-0055 не снимается этим предложением.
